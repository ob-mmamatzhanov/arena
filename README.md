# arena

Авторитетный сервер для real-time 2D-шутера с видом сверху, написанный на Go. Клиенты подключаются по WebSocket, шлют свой ввод, а сервер симулирует мир с частотой 20 тиков в секунду и каждый тик рассылает всем снапшот состояния.

- до 50 комнат по 2–8 игроков: публичные с автозаполнением и приватные по коду, режимы `arena` (все против всех) и `zombie` (вместе против волн зомби); у каждого игрока имя и цвет;
- метрики Prometheus;
- таблица лидеров по фрагам за всё время (Redis или память процесса);
- движение с препятствиями, стрельба с перегревом ствола, рывок (dash);
- пикапы здоровья, ускорения и патронов;
- раунды с лимитом времени и фрагов и перерывом между ними;
- события тика (попадания, убийства, выстрелы) для эффектов на клиенте;
- детерминированная симуляция без аллокаций в горячем цикле.

## Быстрый старт

Нужен Go 1.27+.

```sh
go run ./cmd/server -addr :8080 -origins localhost:5173
```

| Флаг       | По умолчанию | Описание                                                                   |
|------------|--------------|----------------------------------------------------------------------------|
| `-addr`    | `:8080`      | адрес HTTP-сервера                                                         |
| `-origins` | пусто        | разрешённые `Origin` для WebSocket и CORS `/leaderboard`, `/rooms` через запятую, например `localhost:5173` |
| `-redis`   | `$REDIS_URL` | URL Redis для таблицы лидеров, `redis://[user:pass@]host:port/db`; пусто — в памяти |
| `-ip-header` | пусто     | заголовок доверенного прокси с IP клиента для лимита `POST /rooms` (на Fly — `Fly-Client-IP`); пусто — IP соединения |

Хранилище таблицы лидеров выбирается при старте и пишется в лог (`store=redis host=…` или `store=memory`; пароль в лог не попадает). Если URL некорректен или Redis не отвечает, сервер логирует ошибку и работает с таблицей в памяти, которая теряется при перезапуске. На Fly URL задаётся секретом: `fly secrets set REDIS_URL=redis://…`.

Эндпоинты:

- `GET /ws?room=<id>` — WebSocket-подключение к конкретной комнате (нет такой — close-код `4004`); `GET /ws?mode=<arena|zombie>` — автозаполнение: первая публичная комната режима в фазе `play`, `intermission` или `gameover` со свободным местом, иначе новая (неизвестный режим — close-код `4000`); без параметров — `mode=arena`;
- `GET /rooms` — публичные комнаты: `[{ "id": "k3x9q2ab", "mode": "arena", "phase": "play", "players": 3, "maxPlayers": 8 }, …]`;
- `POST /rooms` с `{ "mode": "arena", "maxPlayers": 4, "private": true }` — создать комнату (`mode` — `arena` или `zombie`, `maxPlayers` 2–8) → `201 { "id": "k3x9q2ab", "code": "QWKP" }`; `code` только у приватной: 4 заглавные буквы без `O` и `I`. Не больше 5 запросов в минуту с одного IP (`429` + `Retry-After`), при 50 живых комнатах — `503`, чужой `Origin` — `403`;
- `GET /rooms/by-code/{code}` — `{ "id": … }` приватной комнаты по коду (регистр не важен) или `404`;
- `GET /metrics` — метрики Prometheus: `arena_rooms_active{mode}`, `arena_players_online`, `arena_tick_duration_seconds{room}` (histogram);
- `GET /healthz` — `200 ok`, пока менеджер комнат работает, иначе `503`;
- `GET /leaderboard?n=10` — лучшие `n` игроков (по умолчанию 10, максимум 100) по фрагам за всё время: `[{ "name": "Alice", "score": 42 }, …]`. CORS разрешён тем же `Origin`, что и WebSocket; если хранилище недоступно — `503`.

Комната, в которой 30 с нет ни игроков, ни входящих, останавливается и удаляется (проверка раз в 5 с).

Сервер корректно завершается по `SIGINT`/`SIGTERM`: сначала останавливает комнаты (они закрывают WebSocket-соединения), затем останавливает HTTP-сервер.

## Игровые механики

Значения по умолчанию заданы в `game.DefaultConfig()`.

| Механика    | Параметры                                                                                          |
|-------------|----------------------------------------------------------------------------------------------------|
| Мир         | 800×600: комнаты на 2–4 игроков — карта `arena`, на 5–8 (и автозаполнение) — `arena-large` с дополнительными укрытиями (см. ниже) |
| Игрок       | скорость 200 ед/с, радиус 12, 100 HP; при входе встаёт на свободный спавн карты                    |
| Смерть      | 3 с мёртв (не цель, не двигается, ввод игнорируется), затем респаун на случайном незанятом спавне карты не ближе 150 к убийце |
| Неуязвимость | 1 с после входа, респауна и начала раунда: урона нет, пули гаснут о игрока, стрелять можно          |
| Стрельба    | пуля 500 ед/с, живёт 1,5 с, урон 25, кулдаун 0,2 с; пули гаснут о стены и границы мира. `fire` из ввода действует 0,1 с: без свежего ввода огонь считается отпущенным |
| Перегрев    | каждый выстрел +0,2 heat, остывание 0,5/с; разброс до ±0,25 рад при heat = 1; первый выстрел точен |
| Рывок       | импульс 700 ед/с на 150 мс, кулдаун 3 с                                                             |
| Патроны     | 12 при появлении, респауне и новом раунде, максимум 30; без патронов выстрел невозможен             |
| Пикапы      | `ammo` (+10 патронов) — отдельным потоком раз в 5 с, не больше 2 на карте при 1–2 игроках; при n игроках интервал ×2/n и лимит ×n/2 (8 игроков — раз в 1,25 с, до 8 на карте), патронов на игрока как в дуэли; `health` (+50 HP) и `speed` (×1,6 к скорости на 5 с) — раз в 20 с, не больше 3 на карте, тип взвешенно 60 / 40 %. Появляются в зонах своего типа, не ближе 40 к игроку, 60 к другому пикапу и 50 к краю мира |
| Ящики       | деревянный ящик (`crate`) ломается после 5 попаданий (на `arena-large` — после 10): каждая пуля гаснет о него и снимает 1 прочности, сломанного нет ни для пуль, ни для движения; в начале раунда все ящики восстанавливаются. Кирпичные стены неразрушимы |
| Раунды      | 120 с или до 10 фрагов, затем перерыв 8 с, во время которого мир заморожен                         |

### Режим `zombie`

Та же карта и механики (стрельба, патроны, пикапы, ящики), но игроки вместе отбиваются от волн зомби (`game.ZombieModeConfig`, [`internal/game/zombies.go`](internal/game/zombies.go)):

- пули проходят сквозь игроков — урона друг другу нет; лимитов раунда по времени и фрагам нет;
- первая волна — через 5 с после входа первого игрока: 2 зомби (разминочная), каждая следующая +2 зомби и +5 ед/с скорости (первая — 90 ед/с); между волнами пауза 10 с, волна кончается, когда убиты все её зомби;
- зомби: радиус 12, 30 HP (две пули), появляется у края карты не в препятствии и не ближе 200 к живым игрокам; убийство даёт стрелку +1 к `score`;
- зомби идут по flow field: сетка 20 px, BFS от живых игроков в обход препятствий (щели между ящиками уже тела зомби непроходимы), пересчёт каждые 5 тиков; вблизи игрока — напрямую;
- касание — 10 урона не чаще раза в 0,5 с от одного зомби; неуязвимых не кусают. Убитый зомби игрок мёртв до начала следующей волны;
- все игроки мертвы — `gameover` с номером волны и числом убитых зомби; мир замораживается на 8 с, затем игра начинается заново с первой волны. Если все вышли — игра сбрасывается до входа следующего игрока.

### Карта

Разреженная арена 800×600 для дальних перестрелок, симметричная поворотом на 180° вокруг центра (`game.ArenaMap()` в [`internal/game/maps.go`](internal/game/maps.go)):

- центральное укрытие 100×80;
- две пары ящиков 32×32 с щелью 16 px: игрок в щель не пролезает, а пуля пролетает;
- четыре угловые стены 100×16, за каждой по два спавна, скрытых от центра;
- короткие стенки у середины каждого края.

## Протокол

Все сообщения передаются как JSON в текстовых кадрах WebSocket. Полное описание типов находится в [`internal/net/protocol.go`](internal/net/protocol.go).

### Клиент → сервер: `join`

Первое сообщение после подключения, до любого `Input`:

```json
{ "type": "join", "name": "Alice", "playerKey": "c2V0dGluZ3Mta2V5" }
```

- `name` — имя: 2–16 символов без управляющих, пробелы по краям обрезаются; иначе сервер назначит `Player_<id>`;
- `playerKey` — постоянный ключ игрока в таблице лидеров, до 64 символов. Если он пуст или некорректен, сервер сгенерирует новый и вернёт его в `welcome`; клиенту стоит сохранить ключ (например, в `localStorage`) и присылать при следующих входах, иначе фраги пойдут в новую строку таблицы.

Если `join` не пришёл за 5 секунд или первым пришло другое сообщение, соединение закрывается с кодом `1008 Policy Violation`.

### Клиент → сервер: `Input`

Клиент шлёт ввод каждый свой кадр, даже без изменений: это заодно heartbeat. Если от клиента ничего не приходит 10 секунд, соединение закрывается.

```json
{ "seq": 42, "moveX": 0.7, "moveY": -0.7, "angle": 1.57, "fire": true, "dash": false }
```

- `seq` — монотонный номер ввода; сервер возвращает последний применённый в `lastSeq`, это нужно для client-side prediction и reconciliation;
- `moveX`, `moveY` — направление движения, вектор длиннее 1 нормализуется;
- `angle` — направление взгляда в радианах;
- `fire` — огонь зажат, `dash` — запросить рывок.

Если за тик пришло несколько вводов, применяется самый свежий по `seq`, а флаги `fire` и `dash` объединяются по ИЛИ, чтобы короткие нажатия не терялись. Направление движения действует до следующего ввода, а `fire` — не дольше 0,1 с (тик ввода и один пропущенный): клик, после которого ввод замолк (лаг, фоновая вкладка), даёт один выстрел, а не по выстрелу на каждую перезарядку; удержание огня продлевается каждым вводом.

### Сервер → клиент: `welcome`

Приходит один раз сразу после подключения. Содержит статические данные, нужные клиенту для отрисовки и предсказания движения:

```json
{
  "type": "welcome", "playerId": 3, "room": "k3x9q2ab", "mode": "arena", "tickRate": 20,
  "name": "Alice", "color": 2, "playerKey": "c2V0dGluZ3Mta2V5",
  "width": 800, "height": 600, "speed": 200, "radius": 12,
  "obstacles": [{ "x": 350, "y": 260, "w": 100, "h": 80, "kind": "brick" },
                { "x": 262, "y": 216, "w": 32, "h": 32, "kind": "crate" }, …],
  "crateHits": 5
}
```

У каждого препятствия есть `kind`: `brick` (стена, неразрушима) или `crate` (ящик, ломается после `crateHits` попаданий; `crateHits` = 0 — ящики неразрушимы). Индекс в `obstacles` — номер препятствия в событиях `crateHit`/`crateBroken` и в `snapshot.crates`.

Если комната заполнена (или достигнут лимит комнат при автозаполнении), соединение закрывается с кодом `1013 Try Again Later`.

### Сервер → клиент: `snapshot`

Рассылается каждый тик:

```json
{
  "type": "snapshot", "tick": 1234,
  "players": [{ "id": 3, "name": "Alice", "color": 2, "x": 512, "y": 300, "angle": 1.57, "heat": 0.4, "hp": 75,
                "score": 2, "ammo": 9, "boosted": false, "dashCd": 1.2, "lastSeq": 42,
                "dead": false, "respawnIn": 0, "invuln": false }],
  "bullets": [{ "id": 17, "owner": 3, "x": 520, "y": 330, "vx": 0, "vy": 500 }],
  "pickups": [{ "id": 5, "type": "health", "x": 200, "y": 700 }],
  "crates":  [{ "i": 2, "hp": 3 }, { "i": 4, "hp": 0 }],
  "events":  [{ "type": "hit", "x": 520, "y": 410, "targetId": 4, "shooterId": 3 }],
  "round":   { "phase": "play", "timeLeft": 87.5 }
}
```

Скорость пуль передаётся, чтобы клиент мог экстраполировать их между снапшотами. Поле `events` есть только в тиках, где что-то произошло, и каждое событие приходит ровно в одном снапшоте:

| Событие     | Поля                                  |
|-------------|---------------------------------------|
| `hit`       | `x`, `y`, `targetId`, `shooterId`     |
| `kill`      | `targetId`, `shooterId`               |
| `shot`      | `playerId`, `x`, `y`                  |
| `bulletHit` | `x`, `y` — пуля ударилась о стену, границу или неуязвимого игрока |
| `pickup`    | `playerId`, `pickupType`              |
| `respawn`   | `playerId`, `x`, `y`                  |
| `crateHit`  | `obstacle`, `hp`, `x`, `y` — пуля попала в целый ящик и погасла; `hp` — оставшаяся прочность |
| `crateBroken` | `obstacle`, `x`, `y` — ящик сломан (`x`, `y` — его центр); идёт сразу после своего `crateHit` |
| `zombieKill` | `zombieId`, `shooterId`, `x`, `y` — пуля убила зомби (`x`, `y` — где он стоял) |

`crates` — повреждённые и сломанные ящики: `i` — индекс в `welcome.obstacles`, `hp` — оставшаяся прочность (0 — сломан). Ящики, которых нет в списке, целые; если все целые, поля нет. Список приходит в каждом снапшоте, так что вошедший или переподключившийся клиент сразу видит актуальное состояние.

Во время перерыва `round` выглядит как `{ "phase": "intermission", "timeLeft": 6.0, "winnerId": 3, "scores": [{ "id": 3, "name": "Alice", "score": 10 }] }`. `winnerId` = 0 означает ничью или раунд без фрагов.

В режиме `zombie` снапшот дополнительно содержит `"zombies": [{ "id": 7, "x": 12, "y": 300, "hp": 30, "speed": 90 }]` (поля нет, пока зомби нет), а `round` — `{ "phase": "play", "timeLeft": 4.5, "wave": 2, "zombiesLeft": 0 }` (`timeLeft` — до следующей волны, 0 пока волна идёт) или `{ "phase": "gameover", "timeLeft": 8, "wave": 5, "kills": 31 }` (`timeLeft` — до новой игры). Укус зомби приходит как `hit`/`kill` с `shooterId` 0, ранение зомби не насмерть — как `bulletHit`; у игрока, ждущего волны, `respawnIn` — время до неё (0, пока волна идёт). В `welcome` комнаты `zombie` есть `zombieRadius`.

`color` — индекс 0–7 в палитре клиента. Входящий игрок получает наименее занятый цвет (при равенстве — меньший индекс), а цвет вышедшего освобождается. `playerKey` в снапшоты не попадает.

## Архитектура

```
cmd/server        точка входа: флаги, HTTP, graceful shutdown
internal/game     чистая симуляция: World.Update(dt, inputs), World.Snapshot()
internal/net      JSON-протокол и обёртка над WebSocket-соединением
internal/room     комната: связывает game и net, тикает мир, рассылает снапшоты, пишет фраги
internal/leaderboard  таблица лидеров: Store (память / Redis) и GET /leaderboard
internal/manager  реестр комнат: создание, автозаполнение, коды, удаление пустых; /rooms, /ws, /metrics
internal/cors     проверка Origin для CORS (та же, что у WebSocket)
```

Зависимости направлены строго `manager → room`, `room → game`, `room → net` и `room → leaderboard`, а `game`, `net` и `leaderboard` друг о друге не знают.

- **`game`** — симуляция без I/O и горутин. Вся случайность идёт из генератора с сидом, поэтому прогон воспроизводим. `Update` не аллоцирует память (`0 allocs/op` в бенчмарке).
- **`net`** — в сокет пишет только `WritePump`, остальной код ставит сообщения в очередь неблокирующим `TrySend`.
- **`room`** — одна горутина владеет миром и клиентами и общается с внешним миром только через каналы, поэтому мьютексов нет. Снапшот маршалится один раз на всех, а клиента, у которого переполнена очередь отправки, сервер отключает, чтобы медленные клиенты не тормозили остальных.
- **`manager`** — реестр комнат под одним `sync.RWMutex`; внутрь комнат не лезет, а читает опубликованные ими атомарные счётчики (игроки, занятые места, фаза). Место в комнате резервируется атомарно до входа, поэтому параллельное автозаполнение не переполняет комнаты и не создаёт лишних.

Подробности и инварианты, на которые опирается код, описаны в [`CLAUDE.md`](CLAUDE.md).

## Разработка

```sh
go build ./... && go vet ./... && go test ./...      # проверка перед коммитом
go test -race ./...                                    # гонки в room/net
go test ./internal/game -run '^$' -bench BenchmarkUpdate8Players100Bullets -benchmem
```

На Windows для `-race` нужны cgo и C-компилятор (например, WinLibs MinGW-w64), а также `CGO_ENABLED=1`.
